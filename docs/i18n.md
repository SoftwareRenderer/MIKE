# i18n — Translation Packs and the Derived Language

Read this before touching `frontend/src/lib/i18n/`, the first-run offer
(`frontend/src/lib/utils/locale-offer.ts`,
`frontend/src/lib/services/locale-offer.svelte.ts`, `LocaleOffer.svelte`),
`backend/extensions/i18n.go`, the `i18n` capability in
`backend/extensions/extensions.go`, or the pre-paint scripts in `frontend/index.html`
and `frontend/src/main.ts`.

## The language is derived, never stored

**The active language *is* whichever `i18n` extension is enabled. English when none.**

There is no `language` field in the config, no `PUT /api/config` path for one, no
`language` column, and nothing in IndexedDB that the user chose. That is the
architecture, not an omission: a stored setting would need reconciling with the
extension list forever after, and the two would disagree (a pack disabled while a
setting still named it, a second tab, a restore from a backup). Deriving it means
there is one answer and it is always the current extension list.

The server derives its prompt locale from that same rule: `ActiveI18N` is the only
answer, and `backend/server` hands the winner's `prompts_dir` to `prompts.SetOverlay`
at startup and on every extension change (see "Prompt templates: the overlay"). Both
ends exist because they are one rule with two readers, and nothing stores the result.

## One rule, two ends

`extensions.ActiveI18N` (Go, `backend/extensions/i18n.go`) and `resolveI18NPack`
(TS, `frontend/src/lib/i18n/load-pack.ts`) apply the same rule to the same list:

1. skip any extension that is **disabled** — a disabled pack never contributes text;
2. keep those that **declare `capabilities.i18n`** — the declaration, *not*
   `type === 'i18n'`, because `type` is what `inferExtensionType` inferred for
   routing, so a manifest shipping a catalog alongside something heavier still
   ships a catalog;
3. take the first by `manifest.priority` ascending, then `name` ascending — the
   ordering `HandleList` already sorts the API response by.

The TS side re-sorts rather than trusting incoming order, so the winner cannot
depend on which fetch answered first. `TestActiveI18N` (Go) and the "two enabled
packs" case (`load-pack.unit.svelte.ts`) run over the **same three packs** and must
agree on the winner; that is the check that the rendered UI and the prompt locale
can never name different languages. Change the fixture in one, change it in the other.

Two enabled packs is supported and is not a coin flip: the winner and everything it
ignored are logged (`[i18n] pack-ja → ja (active); ignoring 2 other enabled pack(s)…`).

## A pack is a css pack with different bytes

An `i18n` pack has no iframe, no channel, no permission, and no code path that
executes. It is exactly the `css` type's shape — one manifest asset resolved against
the extension's own directory and applied app-globally
(`ui-injector.svelte.ts`'s `css_url` handling is the precedent):

- The catalog URL is **`resolveAssetURL(ext, cfg.messages_url)`** — the manifest asset
  joined onto the directory the extension is served from, and `''` for anything with a
  scheme or starting `//`. That is the fence that keeps a pack from pointing the app at
  a remote origin — the same argument that stopped a theme extension loading its
  stylesheet from elsewhere. The loader treats `''` as a failure: English, reported.
- The base it joins onto is **`ext.served_url`**, which the server derives from the
  installed record through `extensionDir` (`servedURLFromDir`, `backend/extensions/handler.go`) —
  the same function that reads, deletes and repairs the directory. Never re-derive it
  client-side from `manifest.author`: an unpublished extension placed flat under the
  extensions root is served at `/extensions/<name>`, and a URL guessed from the manifest
  404s its catalog while the pack sits there installed and enabled, leaving the UI in
  English. `extBaseURL` falls back to the author/name guess only when the response
  carries no `served_url`, and rejects a reported value that is not a one- or
  two-segment path under `/extensions/`.
- The file is served by the **existing** `/extensions/…` static tree
  (`backend/server/routes.go`, `noListingFS`). There is deliberately no new route.
- `validateI18N` (`backend/extensions/manifest_validate.go`) refuses the same things
  *before they are stored*, on install and update, and it checks **two** things the
  declaration alone cannot:
  - the shape: a locale that is not a **bare language subtag** (`validateLocale` — "zh",
    never "zh-CN": one pack is one language, and reducing a region would decide for the
    reader whether they wanted Simplified or Traditional), an external or absolute
    `messages_url`, any `.`/`..` segment, a backslash, a control character, a
    megabyte-long path;
  - the files: the catalog must parse as a flat object whose every value is a **translated
    string or a plural table** (`{"one": …, "other": …}` — the shape `Intl.PluralRules`
    selects from; see "What a value may be"), and a declared
    `prompts_dir` must exist and ship `.tmpl` files that parse with
    `prompts.FuncMap()` — parsed, never executed. A pack whose catalog will not parse is
    refused at install rather than discovered in the browser.
  A pack is also **exclusive**: a manifest declaring `i18n` beside any other capability is
  refused, because the pack is the one capability that gets no sandbox, no mounts, no
  network and no permissions, and a manifest that also runs something must not be allowed
  to arrive wearing that exemption. `PUT /api/extensions/{id}` merges no `i18n` field, but
  re-validates the stored declaration on every save, so an extension cannot rewrite its way
  out of validation. Refused, not stored, matching every other manifest rule.

## Loading: whole catalog or English

`loadI18NFromExtensions(extensions)` is called from `ExtensionManager.loadExtensions()`
right after `uiInjector.registerFromExtensions(...)` — the one call that the
`extension_change` broadcast already drives (`App.svelte`), so enabling a pack
switches the language and disabling it switches back, with no reload. The runtime's
active tag is `$state` and every accessor reads it — `t()` for text, `activeLocale()`
for formatting — so there is no version bumper and no `$effect` mirror, and
`document.documentElement.lang` is owned by the runtime.

Failure policy:

- **A catalog is only ever assigned whole.** `parseCatalog` (`catalog.ts`) demands a
  flat object of strings and plural tables inside sane bounds (1 MiB body, 20 000 keys,
  200-char keys, 4000-char values), and `setCatalog` snapshots it. No half-applied pack
  is reachable. The Go side validates the same shape (`validateCatalogValue`,
  `manifest_validate.go`) — a pack the installer refuses for a form the runtime would
  render, or one it accepts for a form the runtime would drop, is the same bug facing the
  other way.
- **A pack that cannot be loaded leaves the UI in English and says so** on
  `console.error` with the reason. Never a UI of raw key ids.
- **One deliberate exception:** if the *same* pack is already on screen and merely
  fails to refresh (a 500, a blip), the working catalog stays and the failure is
  reported — a transient fetch error should not throw a working Chinese UI back to
  English. A *different* winner that fails does fall through to English.
- **A missing key degrades per key**, `pack → en → the id`, warning once per key per
  catalog. A partially translated pack is a normal state, not an error state.
- **A key *nothing* has warns whether or not a pack is installed.** With `t()` typed to
  `MessageKey` an id that reaches the screen has come from a cast or a pack template, and
  both are bugs; a fallback nobody hears is a fallback nobody fixes. Both warnings are
  deduped per key and compiled out of a production build (`import.meta.env.PROD`).

## What a value may be

A catalog value is a translated **string**, or a **plural table** — an object keyed by the
`Intl.PluralRules` categories (`zero`/`one`/`two`/`few`/`many`/`other`) that must contain
`other`, the only category every language has and the only one a single-form language
needs. `en.ts` uses both shapes, so a pack that could only ship strings would leave every
counted string in the UI English in every locale — the one thing a pack exists to fix. A
table naming a category Intl cannot answer with (`onet`), holding a non-string form, or
omitting `other` is refused on both sides: nothing could ever select it.

A language with fewer categories than English is complete, not short, and a form its
`Intl.PluralRules` never answers folds into `other`. That one string owes the **union** of the
placeholders of every English form: dropping a token is a failure, and so is inventing one, because
the caller passes only what the English names. The gate compares such a message as one message, and
compares each form the language does select on its own.

## Two accessors, two different questions

The formatting work (locale-aware numbers, `timeAgo`, the CJK `:lang()` typography) and
the pack loader read **one runtime**, because a second source of "what language are we
in" is exactly the disagreement this design exists to avoid. It answers two questions
that must not be collapsed:

| Accessor | Question | With no pack installed |
|---|---|---|
| `activeLocale()` | what tag to hand `Intl.*` / `toLocale*` | `undefined` = "ask the browser" — the pre-i18n behaviour, so a user with no pack sees no change |
| `documentLanguage()` | what `<html lang>` must say: the language of the **strings rendered** | `en` — never the browser's tag, or `:lang()` typography would restyle an English UI in Japanese |

`resolvedLocale()` is `activeLocale()` with the browser's own tag resolved into it, for
probes and debug output. `locale.code` (and the runtime's own `locale`) is
`documentLanguage()` by another name — the locale the interface is rendering in — and is
what the converted components pair with `t()`. Nothing else in the app computes a locale,
and `setLocale()` is an **in-memory test/preview seam** — it installs no catalog and persists nothing, because
a stored locale would have to be reconciled with the extension list forever (see "The
language is derived, never stored"). The only locale that reaches storage is the
pre-paint hint below, and `cache.ts` owns that.

`$lib/i18n` is the import surface: `t(key, params?)` for components, plus `locale`,
`setCatalog`, `resetToEnglish`, `registerCatalog`, `setLocale`, the two locale accessors
and `onLocaleChange` for the imperative consumers holding cached state. `t()` is typed to
`MessageKey` — every string the UI renders is a core key, so a typo is a build error and
not text on screen — while `packText`/`has`/`hasKey` take `LocaleKey` (`MessageKey | (string
& {})`), because those are asked about keys a pack authors itself, such as the
`` `time.${unit}Ago` `` template `format-time.ts` builds.

Lookup narrows the tag by subtag (`zh-Hans-CN` → `zh-Hans` → `zh`) over a table seeded
with the English record and extended at runtime by `registerCatalog` — a pack is fetched
long after the module was imported, so the table cannot be a static import. The table is a
`SvelteMap`, not a `Map`: `boot.ts` applies the cached catalog under a tag and the first
`loadExtensions()` hands **the same tag** freshly fetched bytes, so a write that leaves the
tag alone still has to re-render. Two rules in there are load-bearing:

- **A pack declaring `en` cannot register.** The English map is the record, not something
  a pack overrides, so `setCatalog('en', …)` is the same as passing `null`.
- **`packText()` answers nothing for a chosen locale that has no pack — and that gap is
  not English.** It is what lets `Intl.RelativeTimeFormat` render `5分前` rather than an
  English `5m ago` in a Japanese UI. `t()` deliberately keeps going to English, because a
  caller with no better answer must still print something readable.

## Pre-paint cache: anticipates, never outranks

The language needs a server round-trip, so the last resolved catalog is cached and
applied before `mount(App)`:

| What | Where | Why there |
|---|---|---|
| The catalog (`{source, locale, messages}`) | IndexedDB `app-settings`, key `i18n-catalog`, via `loadAppSetting`/`saveAppSetting` | All client storage goes through `$lib/storage`; a catalog is far too big for `localStorage` anyway |
| The locale tag alone | `localStorage`, `kanban-i18n-locale`, read by `index.html`'s pre-paint script | `index.html` runs synchronously; IndexedDB cannot. This is the one precedented exception — `kanban-theme-css` already does the same thing for a stylesheet URL, and a 6-character tag is the same kind of value |

Both are written together on a successful apply and **deleted together** whenever the
live list resolves to English — no pack, disabled, uninstalled, or a pack that failed
to load. That delete rule is the whole "cache never outranks reality" property: a pack
that is gone leaves no text behind, so there is no way to boot into a language with no
pack behind it. Clear the cache unconditionally on that path — an earlier version
skipped the delete when it *believed* the cache was already empty, and that guess
survived a stale entry from a previous session. The same reasoning is why the loader
resets the **tag** unconditionally: `runtime.svelte.ts` adopts the tag the pre-paint
script painted, so a reconcile that finds no pack must take that tag back even when no
catalog was ever applied in this cycle.

The runtime **adopts** that pre-paint tag rather than overwriting it. `index.html` has
already written the cached tag into `<html lang>` before any module runs, and a
module-scope `syncDocumentLanguage()` (which is all this file used to do at import)
stamped `en` back over it one frame later — so a reload flashed out of the pack's
language and back again, in the one configuration the cache exists to serve.
`prePaintTag` reads the document (never storage) and seeds the runtime with it, which
leaves `<html lang>` with exactly one writer after boot and a first frame that is
already correct. A frame-by-frame probe of a reload is what caught this: the tags seen
before the app mounted went from `[zh, en]` to `[zh]`.

`applyCachedCatalog` (`boot.ts`) re-validates through `parseCatalog` on the way out and
gives up after 250 ms: a database that will not answer must delay the language, never
block the mount. Whatever it applies is replaced by the first `loadExtensions()` —
including being replaced by English.

## The first-run offer: the offer is derived, never stored

A browser whose language has a pack **in the registry** is *offered* that pack, in
one line of chrome with two buttons: install, and don't ask again. The click is the
consent — nothing installs silently, because installing is fetching someone else's
catalog and switching the language of the whole app.

The offer is shown only when **all four** hold (`resolveLocaleOffer`,
`frontend/src/lib/utils/locale-offer.ts`, pure):

1. **no i18n pack is enabled** — English *is* the no-pack state, and the rule is the
   loader's own (`resolveI18NPack`), so it is the capability declaration and the
   enabled flag, never `type === 'i18n'`;
2. the browser's primary language subtag is not `DEFAULT_LOCALE`;
3. the registry index carries a pack whose **projected** `capabilities.i18n.locale`
   answers that subtag. One comparison, the primary subtag on both sides — which works
   because a pack may only declare one bare subtag (see the validator above), so one
   browser language can name exactly one language to offer. Ties break on name so the
   offer cannot depend on the order the index arrived in, and the entry's tag is read
   through the same subtag function on purpose: the index is a published file, not a
   validated one, so an entry generated before the bare-subtag rule still reaches the
   reader it was written for rather than making the offer go quiet;
4. no record of having asked exists in IndexedDB `app-settings` under
   `locale-offer` — `dismissed`, `installed` **or `failed`**.

The parts that are easy to get wrong:

- **No match means no word, ever.** No matching pack, no registry, a registry that
  will not answer (`MIKE_REGISTRY_URL` is a bare local path in tests and simply
  unreachable offline), a browser with no readable language: all of them are
  silence, logged at `[i18n] no language pack offered (<reason>)`. That is also why
  the service calls `getRegistryIndex()` itself rather than going through the
  extension list's own load — a registry failure must not surface anywhere the
  user did not ask about.
- **A `failed` record is not a retry counter.** A broken registry or an
  uninstallable pack must not re-ask on every boot, so a failure ends the
  conversation like a dismissal does and the toast says it once.
- **An installed pack suppresses its own offer**, enabled or not: `POST /install`
  answers 409 for a pack that is already there, and a pack the user *disabled* was
  their decision to go back to English.
- **Detection runs after `loadExtensions()` resolves** (`session-boot.svelte.ts`, chained onto
  both boot-time calls). Run earlier, condition 1 reads the previous session's
  extension list and offers a pack that is already on. One pass per boot —
  `loadExtensions()` also runs on every `extension_change`, and an offer that comes
  back after the user answered it is a nag.
- **The install is the existing git-pinned one.** `installExtension(name)` over the
  operation's SSE stream, so the progress line is the server's own steps; the
  install lands enabled, the `extension_change` broadcast reloads the list, and
  `loadI18NFromExtensions` switches the language live. There is deliberately no
  second install path and no `language` anything could persist.
- **The offer's own text is English** (`i18n.offer.*` in `en.ts`) because it is only
  ever shown with no pack installed — a translated copy is exactly what the user has
  not got yet. The only language name it can print is the registry entry's
  `display_name`, verbatim (that is why the published packs name themselves
  `日本語`/`한국어`/`简体中文` in their own manifests).

`scripts/gen-registry.py` projects `i18n: { locale, messages_url, has_prompts }` into the
registry index for exactly this reason: the locale match has to be computable **before**
anything is fetched, and `has_prompts` is disclosed in the same breath because a translated
interface with English prompts is a different offer than a fully translated one. The
catalog itself and every translated string stay in the pack.

**Known residual:** the card floats bottom-right at `z-index: 900` — below a modal,
above the bottom-docked terminal panel — so with the terminal open it covers that
panel's right corner. Deliberate: every other position is more crowded (toasts and
the service-worker bar own bottom-centre), the card is one click from gone either
way, and lifting it above the terminal would mean the offer knowing the terminal's
resizable height. Don't "fix" it by making it a modal — an offer that blocks the
board is a different product decision.

## Prompt templates: the overlay

A pack may ship translated prompt templates beside its catalog: `prompts_dir` names a
directory of the same `*.tmpl` files core ships, and the server renders those instead of
the English ones. The overlay lives in `backend/prompts/overlay.go`.

**Injected, never imported.** `backend/extensions` already imports `backend/prompts` for
`FuncMap()` (the install check parses pack templates with it), so `prompts` importing
`extensions` to ask who is active would be a cycle. Instead the server resolves the answer
and *pushes* it: `extensions.ActivePromptOverlay(store, extensionsDir)` →
`prompts.SetOverlay(dir, locale)`, called from `(*Server).refreshPromptLocale()` at startup
and inside the existing `SetOnExtensionChanged` callback. Enabling a pack therefore changes
the language of the next turn with no restart, and `prompts` still knows nothing about
extensions, packs, or which languages exist.

**Resolved per template, pack first then core.** `applyOverlay` parses core's files, then
calls `ParseFiles` on each pack file *one at a time*. text/template replaces a same-named
definition and leaves the set untouched when a file fails to parse — verified against the
real templates in `overlay_test.go` — so:

- a pack shipping only `base.tmpl` still gets core's `summarize.tmpl`;
- a pack file that cannot parse loses **only its own template**, which stays core English;
- a pack file that parses but fails to **execute** on the real turn's data costs the render
  one extra core-only parse and answers in English. A translation must never fail a turn.

Every failure is logged **once per (pack, kind, template)** — a pack that cannot render says
so loudly once, then gets on with answering in English. Parse failures are normally
unreachable (install refuses them — see the validation section), so the runtime path is
defence for files changed on disk after install, not the ordinary route.

**Sub-templates resolve by the name a file *defines*.** `base.tmpl` calls
`{{template "plan-mode" .}}` and `{{template "explore-mode" .}}`, and each name comes from the
`{{define}}` inside `plan-mode.tmpl` and `explore-mode.tmpl` — not from a file name. So the system
prompt parses core's whole glob: a pack's translated `base.tmpl` keeps working against core's
English mode sections, and a pack that translates one keeps its `{{define}}` name. A pack that
invokes a section but ships no file for it renders that section in English, and
`scripts/i18nparity` reports the missing file. Pinned by
`TestPackBaseTemplateResolvesCoreSubTemplates`.

**The state is immutable and read concurrently** (`atomic.Pointer`): prompts render for
every running task, so a render reads one consistent `(dir, locale)` pair for its whole
life. `SetOverlay("", "")` is English and byte-for-byte today's behaviour — asserted, not
claimed, by `TestNoOverlayRendersCoreBytesForEveryEntryPoint`, which compares every entry
point against a plain core parse.

**The directory is contained twice**, like the delete path: `PromptDirInPack` takes the
lexical `packFilePath` proof and then re-checks containment with symlinks resolved, so
neither a `../` nor a symlinked pack directory hands the server a template directory it
was never granted. A refused `prompts_dir` loses the templates and **keeps the locale** —
the language is derived from which pack is enabled, while the directory is a path a
manifest named.

One caveat a local install teaches you: the directory comes from the **row's** `author`, but a
local install leaves files where a human put them and records the **slugged** author — so a pack
staged at `extensions/TestDev/x/` names a directory that does not exist. `install-local` refuses
that folder now, naming the slug to rename it to; before that it installed "successfully" and
every reader of that path failed independently and quietly (templates here, catalog and
stylesheet per "A pack is a css pack with different bytes").

## Not here (and not an oversight)

- **`en.ts` holds only the keys the UI renders.** It is the catalog of record and the
  per-key fallback — one English map, deliberately not duplicated per module — and the
  UI-string conversion task moves component literals into keys and brings their English
  with them; it is not seeded ahead of that. Core holds
  **zero translated strings** and **zero language names** — a locale tag is carried
  through verbatim and never mapped to a display name (Settings shows the tag, the
  offer shows the pack's own `display_name`). That is measured, not remembered:
  `cd frontend && python3 i18n-gate.py` fails on a locale tag, a non-Latin codepoint,
  an `Intl.DisplayNames` call or a `locale === 'xx'` branch anywhere in `src/` outside
  a test fixture (the `:lang(…)` typography selectors in `app.css` are the one
  documented allowance — see `src/lib/i18n/README.md`). The textual tag check covers
  the tags that cannot be mistaken for prose — `zh`/`fr`/`ja`/`ko` and their region
  forms; a Latin-script pack tag like `tr` or `it` IS ordinary prose, so those eight
  languages are held by the branch check, which reads the shape of the comparison and
  so needs no list of languages at all (the measurement is recorded in `i18n-gate.py`).
- **Pack translations are machine-grade and unreviewed.** No native reader has read any
  of the twelve packs — `zh`/`fr`/`ko`/`ja` and the eight that joined them
  (`es`/`de`/`pt`/`it`/`nl`/`ru`/`pl`/`tr`) — and each now ships the `REVIEW.md` that names
  the values waiting for that reading.
  Nothing measures whether a sentence reads well.
  What *is* measured is the pack's shape: `scripts/i18nparity` (`make i18n-parity
  PACK=../MIKE-extensions/i18n/fr`) compares one pack against the English contract and
  fails on a missing or invented key, a value that changed shape or placeholders, a plural
  form the pack's language can never select, a prompt overlay that lost or renamed a
  `{{define}}` or moved a directive, and a pack that is not published in the generated
  registry; it warns on a missing `REVIEW.md` and on a value byte-identical to English that
  looks like prose rather than a shared token. A pack that reads as machine output is not a
  defect any of that can detect, so it is recorded here instead of fixed by a check.
- **Publishing a pack is `../MIKE-extensions`' business**, not this tree's — the
  generator emits an entry for whatever `i18n/<name>/manifest.json` that repo
  **commits**, and a pin it cannot resolve to committed content is a refusal, not a
  warning: `python3 scripts/gen-registry.py` exits naming the pack until that repo
  contains it. So an uncommitted pack is absent from `registry.json`, and the first-run
  offer cannot see a pack the index does not carry. This repo ships no catalog of its own
  and `registry.json` is never hand-edited.

## Manual gate (no spec covers this; do it by hand after changing the loader)

E2E can't cover it cheaply - it needs a pack installed against a real server, and
the check is one browser's worth of `document.documentElement.lang`. Against
`make run` (http://localhost:3000 — that name, not `127.0.0.1`, which no passkey can be bound to; pair
with the code it prints on a fresh install):

1. Write a fixture pack into `extensions/<author>/<name>/` - `manifest.json` with
   `capabilities.i18n: { locale, messages_url }` plus the catalog file. It has to
   live there: a local install is *found* in the installed-extensions tree, and
   uninstalling deletes the directory, because that directory **is** the extension.
   Run the gate twice if you can: once namespaced, once **flat** at
   `extensions/<name>/` (install it with `author: "local"`). The two are served from
   different URLs, and only the API's `served_url` knows which - a client that
   assumes `<author>/<name>` fetches the flat pack's catalog from a 404.
2. `POST /api/extensions/install-local {author, name}` (or Settings → Extensions).
3. Watch, **without reloading**: `document.documentElement.lang` becomes the pack's
   locale, the console logs `[i18n] <name> → <locale>`, and a 200 comes back for
   `<served_url>/<messages_url>` (that response is the proof there is
   no new route).
4. Toggle it off in Settings → Extensions → English again, same tab, no reload, and
   both cache entries (`app-settings` `i18n-catalog`, `localStorage`
   `kanban-i18n-locale`) are gone. Toggle on → back. Uninstall → English again.
5. Reload while enabled and read `document.documentElement.lang` at
   `DOMContentLoaded`: it must already be the pack's locale, which is the only thing
   that distinguishes the pre-paint cache from the extension-list round-trip. Read it
   **per frame until the app mounts**, not once at the end - the failure this catches
   is a frame in the middle. An `addInitScript` that pushes
   `[document.documentElement.lang, !!document.querySelector('#app > *')]` on every
   `requestAnimationFrame` and stops at the mounted one is enough, and the assertion
   is that no unmounted frame says `en`.
6. `make stop` and check `pgrep -xc mike` is 0, then delete the fixture.

The prompt half is checked in the same session by reading the server log, which is where
the derived language announces itself: `[prompts] locale=en (no translation pack enabled)`
at boot, `[prompts] locale=<tag> templates=<dir>` once the pack is enabled, and back to
`en` on disable or uninstall — all without a restart. A pack whose `prompts_dir` names
something outside its own directory logs `… is not a directory inside the pack — prompts
stay English` and keeps the locale. (Rendering a translated prompt end to end needs a task
against a mock LLM; `backend/prompts/overlay_test.go` renders the real templates instead,
and `backend/server/prompt_locale_test.go` pins that enabling a pack moves the overlay.)

Toggling a pack now changes every label the pack translated, per key: the UI-string
conversion is finished and `cd frontend && python3 i18n-count.py` measures zero core-owned literals, so
there is no longer a body of chrome sitting in English while it waits for a later batch.
What stays English by design is what core does not own — `en.ts`'s own English (the
fallback), the `i18n.offer.*` block (which by definition renders only with no pack
installed), and whatever an installed extension authors in its own files. A key the pack
omits falls back per key, which is the expected shape of a partial pack, not a broken
loader.

The offer itself does have a spec (`e2e/i18n-first-run-offer.spec.ts`), because it
needs the registry fixture, a browser locale, and a git-pinned install to be worth
anything; the steps above are for the loader, which it does not re-cover.

## The asset-path fence (pack URLs)

A pack is a css pack with different bytes: the catalog URL is `resolveAssetURL` over **`ext.served_url`** —
the directory the server derives from the installed record through the same `extensionDir` it reads and
deletes through. A client-side guess from `manifest.author` 404s the catalog of any extension not laid down
at `<author-slug>/<name>` (a flat local install is served at `/extensions/<name>`), which reads as an
installed, enabled pack that never translated anything.

`''` for a scheme, a `//`, **or any path that leaves that directory once `..` is resolved** is the fence.
The browser normalizes dot segments before it sends, so an unresolved concatenation of the base and
`../../../../api/config` is an authenticated same-origin request for `/api/config`, made by the app with its
own cookie; the answer is contained against the base's own normalized form. `isPrepaintableThemeURL` (plus
its hand-copied twin in `index.html`, which runs before any module can) refuses dot segments,
`%2e%2e`/`%2F`, `?` and `#`. `capabilities.css.css_url` and `capabilities.i18n.messages_url` are held to the
same shape server-side by `validateAssetRelPath` (`manifest_validate.go`). There is no new route, no iframe,
no channel, no permission.

Both halves validate a catalog value's shape — a string, or a plural table with `other` required:
`parseCatalog` (TS) and `validateCatalogValue` (Go). Refusing a pack for a form the runtime would render,
or accepting one for a form it would silently drop, is the same bug facing the other way.

## Frontend locale and formatting

- Formatting follows `activeLocale()` from `$lib/i18n/runtime.svelte`; **sorting does not**. Pass
  `activeLocale()` to every `Intl.*` / `toLocale*` call — never `undefined`, `[]` or a literal tag at a call
  site; this grep must stay empty outside `__tests__`:
  `grep -nE "new Intl\.[A-Za-z]+Format\(\s*(undefined|\[\])?\s*[,)]|toLocale(A|S|D)[A-Za-z]*\(\s*(undefined|\[\])?\s*[,)]" frontend/src`.
- **Never cache anything locale-derived at module scope.** One `let` computed at module load pins the first
  value for the whole session. Compute per call, or memoise **keyed by the locale** (`usdSymbolByLocale`).
- **Sorting is locale-independent on purpose.** Every `localeCompare` keeps its current arguments
  (`Sidebar`, `FileBrowserView` — the file listing both explorers render, `BranchSymbols`,
  `Chat/ModelSelector`, `DiffViewer.svelte`, `GitStatusPanel`): file, branch, symbol, session and model lists must stay stably ordered whatever the UI
  language is. Model *grouping* groups by provider, never by collation.
- Relative time uses `Intl.RelativeTimeFormat(locale, { style: 'narrow' })` — `narrow` yields `5m ago`, and
  `long` would print `5 minutes ago` and break the shape the chat stats line and the unit tests pin.
  `formatElapsed`/`formatDuration` stay unlocalised for the same reason.
- **`packText()` answers nothing for a chosen locale that has no pack — and that is not English.** The gap
  is what lets `Intl` render the number in the locale the user is in instead of an English phrase in the
  wrong language; `t()` keeps the English fallback because a caller with no better answer must still print
  something. Both read the same runtime as the packs, which stays the only writer of the active locale:
  `setLocale()` is an in-memory test/preview seam and persists nothing.
- Core gains zero translated strings and zero language names, measured by
  `cd frontend && python3 i18n-gate.py`, and zero literal UI strings, measured by
  `cd frontend && python3 i18n-count.py` — with `i18n-count_test.py` pinning each exclusion
  rule in both directions so the gate cannot go blind to real copy. The attributes a control is named by
  are part of that surface, and `docs/i18n.md → Attribute text is a catalog key` measures them.
- Tests: `frontend/src/lib/i18n/__tests__/runtime.unit.ts` (interpolation, per-locale plurals, the fallback
  ladder and its warnings, `<html lang>`), `runtime.unit.svelte.ts` (reactivity),
  `frontend/src/lib/utils/__tests__/format-time.unit.ts`, `format.unit.ts`.

## Attribute text is a catalog key

**An `aria-label`, `alt`, `placeholder` or `title` on a tag carries a `t(…)` call or a variable — never a
literal of its own.**

The accessible name is the only copy a person using a screen reader is given, and on an icon-only control the
tooltip is the only hover affordance. One left in English is a half-translated app whatever the label beside
it says.

```bash
cd frontend && python3 i18n-count.py         # each finding: file:line, the attribute, the literal
cd frontend && python3 i18n-count_test.py    # every exclusion asserted in both directions
```

`make test-frontend` runs both, as `npm run check:i18n-surface-test` then `check:i18n-surface`. The counter
reports these literals beside the visible-copy candidates it already measured, through the same tag walker,
comment stripper and string scanner. A second parser would be a second opinion, and the two drift.

The rule is keyed on the attribute **name**, which is what keeps the lookalikes out. `tag_attributes` reads
each tag's attributes and hands `aria-label`, `alt`, `placeholder` and `title` to `text_attr_items`, and
leaves the rest alone: `aria-labelledby` and `aria-describedby` carry an element id, and `aria-hidden`,
`aria-expanded` and `role` carry a flag, so none of them is text and none is measured. `alt=""` stays — it is
how markup says *decorative*.

`is_rendered_literal` then asks whether the literal is what the attribute renders. A value sitting inside a
bracket is not, so the attribute's own text is the only thing measured:

- `t('a.key')` — the accessor's argument is a key, not copy, and `t(open ? 'a.key' : 'b.key')` is the same
  key chosen per frame.
- a comparison (`title={mode === 'rw' ? t('sandbox.readWrite') : …}`) or a lookup key
  (`title={isCollapsed('staged') ? …}`).
- a separator: `sentences.join(' · ')`, and any literal with no letter outside its `${…}` holes.
- `''` — the way a tooltip says "none this frame", which is why `title={stamp ? absolute(stamp) : ''}` is
  a shape and not a hole.

Copy written into one of those positions is still copy, so write it at the attribute instead. A quoted value
is a finding wherever the attribute renders it. That covers `title={'Stage changes'}`, both arms of
`title={ok ? 'Stage' : 'Unstage'}`, a literal after `+`, and a literal on a component tag
(`<BaseModal title="…">`), because that prop renders.

**What it refuses to see.** A literal in another function's argument — `title={helper('Save now')}` — reads
as a lookup key, because that shape is a key more often than it is copy. Only `.svelte` templates are
scanned. A name assembled outside the render path — `{ ariaLabel: 'Close' }`, an imperative `el.title`, a
prop default — belongs to the module that owns it, and `frontend/src/lib/i18n/README.md` states how those
recompute on a language switch. `<script>` blocks and `.ts` modules are still measured, but by the shape of
the string rather than by its position.

**The ratchet.** The `placeholder` values that are format examples — `/host/path`,
`docker.io/ubuntu:latest`, `https://github.com/org/repo.git` — are allowed by one `TEXT_ATTR_ALLOW`
entry each, keyed by file, attribute and literal, with the reason beside it. The example is the answer's
shape, and translating it teaches the wrong one. `stale_allow_keys` fails the run when a converted site
leaves its entry behind, so the list only ever shrinks. `frontend/src/lib/i18n/README.md` holds the same
rule for whoever writes the attribute, and it is the prose this section measures.
